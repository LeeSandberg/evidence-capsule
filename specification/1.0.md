# Evidence Capsule 1.0 alpha.3

An Evidence Capsule is a portable record of a conclusion and its support. The
format does not assert that a conclusion is true. It makes its support,
assumptions, policy decisions, origin, and revision relationship inspectable.

## Canonical payload

For alpha.2 and alpha.3, remove the top-level `integrity`, `signatures`, and
`approvals` fields, serialize the remaining object as UTF-8 JSON with
lexicographically sorted keys, no insignificant whitespace, finite JSON numbers,
and `ensure_ascii=false`, then calculate SHA-256. Prefix the lowercase
hexadecimal digest with `sha256:`.

Alpha.1 verification retains its original rule: only `integrity` is removed.
Array order is significant. Producers must establish deterministic ordering
before hashing when their source store does not preserve semantic order.

## Extensions

Alpha.3 requires an `extensions` array. Each extension is an integrity-covered
object with exactly these fields:

- `uri`: an absolute identifier; `file:` and `javascript:` are forbidden.
- `version`: a semantic version.
- `critical`: whether a consumer must understand the extension before relying
  on the capsule for a decision affected by it.
- `payload`: finite JSON data, bounded by the verifier to 256 KiB canonically.

A capsule may contain at most 128 extensions. Verification never executes
extension payloads or grants capabilities. Unknown optional extensions may be
preserved losslessly. A consumer must block a decision affected by an unknown
critical extension. Alpha.1 and alpha.2 reject an `extensions` field rather than
silently changing their semantics.

## Revisions

Revision 1 uses a null or absent `previous_revision_hash`. A later revision sets
`previous_revision_hash` to the complete `integrity.content_hash` of its
immediate predecessor. A correction creates a new revision; it never mutates an
already distributed signed revision.

## Privacy

Evidence may be represented by a permission-scoped reference and content hash.
The format never requires private documents or personal information to be
embedded. A reference contains an absolute `uri`, `sha256:` content hash,
media type, and `private`, `restricted`, or `public` disclosure
classification. Verification does not claim that unavailable referenced content
was inspected.

## Signatures and approvals

Alpha.2 and alpha.3 signatures use profile
`evidence-capsule-signature/1`, algorithm `Ed25519`, a base64 raw 32-byte
public key, the exact capsule content hash, key identifier, signing time, signer,
and role. The signature covers every signature field except `signature`,
serialized canonically and prefixed by
`evidence-capsule-signature/v1` followed by a zero byte.

Approvals use `evidence-capsule-approval/1` and the equivalent domain separator
`evidence-capsule-approval/v1`. The signed statement includes the exact content
hash, revision, decision, reviewer, note, key and signing time. Valid decisions
are `approved`, `rejected`, and `needs_changes`.

Signatures and approvals are detached attestations: they can be added without
changing the content hash. They cannot alter claims, evidence, extensions,
policies, or provenance without invalidating that hash. A valid embedded-key
signature proves key control, not that an untrusted key belongs to a claimed
legal identity.

## Security status

Alpha.3 cryptographically verifies content attestations and extension integrity.
Identity trust requires an external key registry, certificate, organization
policy, or prior trusted key exchange. Consumers must report key-control
verification and identity trust as separate results.
